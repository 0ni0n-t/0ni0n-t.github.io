이 글은 공부 방법과 진행 방식만 다룹니다. 아직 제보하지 않았거나 공개 승인이 없는 내용은 적지 않습니다.

## 1. 이 활동을 하게 된 계기

저는 결과로 인정받는 활동을 고르려고 합니다. 버그바운티는 찾은 취약점이 실제로 의미가 있으면 보상으로 돌아오기 때문에, 제 실력이 바깥에서 통하는지 확인하기 좋은 방법이라고 생각했습니다.
또 공부하는 분야가 클라우드 보안이라, 클라우드 서비스를 운영하는 회사의 프로그램에 도전해 보고 싶었습니다.

## 2. 시작하기 전 처음 질문

| 질문 | 시작 전 내 생각 |
|---|---|
| 어떤 프로그램부터 해야 할까? | 보상이 큰 곳이 좋을 것 같다 |
| 어디까지 테스트해도 될까? | 사이트에 적힌 도메인이면 다 될 것 같다 |
| 실제 서비스를 건드리지 않고 연구할 수 있을까? | 잘 모르겠다 |
| 처음 하는 사람은 무엇부터 해야 할까? | 스캐너를 돌리면 뭔가 나올 것 같다 |

시작해 보니 네 개 모두 생각과 달랐습니다.

## 3. 어떻게 했고 어떤 결과가 나왔나

### 3-1. 프로그램을 기간으로 나눠 골랐습니다

보상만 보고 고르면 경쟁이 심하거나 너무 어려운 곳만 남습니다. 그래서 결과를 빨리 볼 수 있는 곳 하나와 오래 붙잡을 곳 하나로 나눴습니다.

| 구분 | 프로그램 | 고른 이유 |
|---|---|---|
| 빨리 | MongoDB (HackerOne 공개 프로그램) | 클라우드 서비스와 오픈소스 코드가 함께 범위에 있음 |
| 오래 | Google Cloud VRP | 제 관심 분야(클라우드 격리, 가상화)와 맞고 보상 상한이 큼 |

### 3-2. 프로그램별 scope 문서를 만들었습니다

프로그램마다 정책을 정리한 scope 문서를 따로 만들었습니다. 들어가는 내용은 이렇습니다.

- 범위 안 자산과 범위 밖 자산
- 허용되는 기법과 금지되는 기법 (예: 서비스 거부와 다른 고객 데이터 접근 금지, 자동 스캐너는 가급적 피하기)
- 요청에 붙여야 하는 식별 헤더, 테스트 계정을 만드는 규칙
- 정책을 확인한 날짜

정리해 보니 처음 생각과 많이 달랐습니다. 도메인이 범위 안이어도 일부 서브도메인은 테스트 자체가 금지돼 있었고, 자동 스캐너는 가급적 피하라고 안내돼 있었습니다. 어떤 프로그램은 일정 점수(Signal) 이상이어야 정식 보고서를 낼 수 있었습니다. 정책은 자주 바뀌기 때문에, 시작할 때마다 다시 확인하는 것을 규칙으로 정했습니다.

### 3-3. 실제 서비스 대신 격리 랩에서 시작했습니다

실제 서비스에 요청을 보내기 전에, 범위 안에 있는 공개 오픈소스 라이브러리부터 보기로 했습니다. 코드가 공개돼 있으면 제 환경에서 마음껏 실험할 수 있기 때문입니다.

1. 정적 분석으로 외부에서 들어온 데이터를 직접 해석하는 부분을 찾았습니다.
2. 그 부분만 겨냥한 퍼징 하네스를 만들고, clang + AddressSanitizer + libFuzzer로 빌드했습니다.
3. 퍼징은 네트워크를 완전히 끊은 VM 안에서만 돌렸습니다.
4. 정적 분석에서 나온 의심 지점은 가능성 순서로 정리하고, 이미 막혀 있는지 하나씩 확인했습니다.

중간에 막힌 점도 있었습니다. 처음에는 퍼저의 커버리지가 2에서 움직이지 않았습니다. 하네스만 계측하고 라이브러리 본체는 계측하지 않아서였습니다. 라이브러리 전체를 계측해서 다시 빌드하니 84로 올라갔습니다. 퍼저가 돌아가는 것과 제대로 탐색하는 것은 다르다는 것을 배웠습니다.

정적 분석에서 찾은 의심 지점은 대부분 다른 곳의 경계 검사에 이미 막혀 있었습니다. 코드 한 줄만 보고 취약점이라고 판단하면 안 되고, 데이터가 실제로 그 지점까지 갈 수 있는지 끝까지 따라가야 한다는 것을 알게 되었습니다.

### 3-4. 결과

- 만든 것: scope 문서 2개, 퍼징 하네스와 격리 랩, 의심 지점 목록
- 제출한 보고서: 0건
- 받은 보상: 0원

크래시가 나온 적도 있지만, 아직 원인 분석과 제보 전이라 이 글에는 적지 않습니다.

## 4. 부족했던 점

- 아직 보고서를 한 번도 내지 못했습니다. 준비와 환경 만들기에 시간을 많이 썼습니다.
- 오픈소스 퍼징에 치우쳐서, 웹과 API의 권한 문제처럼 클라우드 서비스에서 자주 나오는 취약점은 직접 해 보지 못했습니다.
- 크래시가 나왔을 때 원인을 찾고 영향을 판단하는 트리아지 경험이 부족합니다.
- 다른 사람이 공개한 보고서를 더 읽고, 어떤 보고서가 인정받는지 살펴봐야 합니다.

## 5. 앞으로 할 것

- 공개된 보고서를 읽고, 취약점 유형별로 어떤 근거와 재현 절차를 썼는지 정리하겠습니다.
- 정책이 허용하는 본인 테스트 계정 안에서 권한 분리와 테넌트 격리를 점검해 보겠습니다.
- 퍼징 크래시는 원인 분석부터 끝까지 해 보고, 의미가 있으면 정책에 따라 제보하겠습니다.
- 첫 보고서 제출을 목표로 하고, 공개가 허용되면 그 과정을 이 카테고리에 다시 쓰겠습니다.
