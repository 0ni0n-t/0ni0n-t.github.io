## 0. 이 논문을 고른 이유

저는 지금 **"VM escape 이후 QEMU 프로세스의 이상 행위를 eBPF로 탐지하는 도구"** 를 만들고, 그 도구로 논문을 쓰는 프로젝트를 하고 있습니다. 탐지 도구를 만들다 보면 이런 질문을 피할 수 없습니다.

> "공격자가 내 감시 도구보다 높은 권한을 얻으면, 감시 도구가 남긴 기록은 믿을 수 있을까?"

HyperAudit은 이 질문을 정면으로 다룬 논문입니다. 그래서 제 프로젝트의 위협 모델을 다시 점검하려고 이 논문을 골랐습니다.

## 1. 읽기 전에 먼저 정리한 것

미션 안내대로 논문을 읽기 전에 세 가지를 먼저 적어 봤습니다.

| 질문 | 읽기 전 내 답 |
|---|---|
| 이 논문이 다루는 문제는? | 클라우드 VM 안에서 동작하는 감사(로그 수집) 도구가, 커널을 장악한 공격자에게 로그를 지워질 수 있다는 문제 |
| 왜 중요한가? | 사고 조사는 "공격자가 들어오기 직전에 무슨 일이 있었나"를 봐야 하는데, 그 기록이 사라지면 조사 자체가 불가능해짐 |
| 기존 방식은 무엇이 부족했나? | 로그를 아주 자주 안전한 곳으로 옮겨서 버티는데, 그만큼 느려짐 (보안과 성능 중 하나를 포기) |

읽고 나니 큰 방향은 맞았고, "왜 느려질 수밖에 없었는지"의 원인을 논문이 한 줄로 정리해 준 점이 인상적이었습니다(2장에서 설명합니다).

## 2. 들어가기 전에: 꼭 필요한 개념 5개

처음 보는 분도 따라올 수 있게, 이 논문을 읽는 데 필요한 개념만 짧게 정리합니다.

**① 시스템 콜(syscall)과 감사 로그**
프로그램이 파일을 열거나(`openat`), 다른 프로그램을 실행하거나(`execve`), 네트워크 연결을 만들 때는 커널에게 부탁해야 합니다. 이 부탁이 시스템 콜입니다. 감사(auditing) 도구는 "누가, 언제, 어떤 시스템 콜을, 어떤 인자로 불렀고 결과가 무엇이었나"를 기록합니다. 예를 들면 이런 한 줄입니다.

```
10:02:03  PID 421  execve("/usr/bin/bash")  = 0
```

이 한 줄만으로 공격이라고 할 수는 없지만, 이런 기록을 이어 붙이면 공격 경로를 되짚을 수 있습니다.

**② 버퍼와 "아직 저장되지 않은 로그"**
로그는 생기자마자 디스크에 바로 써지지 않습니다. 먼저 메모리의 임시 공간(버퍼)에 쌓였다가, 나중에 한꺼번에 저장됩니다. 이 "버퍼에 머무는 시간" 동안 로그는 아직 안전하지 않습니다.

**③ 하이퍼바이저**
VM을 만들고 관리하는 계층입니다(KVM 등). 게스트 VM의 커널보다 **한 단계 높은 권한**에서 동작하기 때문에, 게스트 커널을 장악한 공격자도 하이퍼바이저는 마음대로 건드리지 못합니다.

**④ 2단계 주소 변환(stage-1 / stage-2 페이지 테이블)**
VM 안의 프로그램이 메모리 주소에 접근하면, 주소가 두 번 바뀝니다.

```
게스트 가상 주소 ──(stage-1, 게스트 커널이 관리)──▶ 게스트 물리 주소
                 ──(stage-2, 하이퍼바이저가 관리)──▶ 실제 물리 주소
```

핵심은 **stage-2는 하이퍼바이저 것**이라는 점입니다. 게스트 커널이 stage-1을 아무리 고쳐도, stage-2에서 "여긴 읽기 금지"라고 막아두면 접근하는 순간 하이퍼바이저로 걸립니다(trap).

**⑤ 실행 전용(XO) 권한과 가드 페이지**
- XO(execute-only): 코드를 *실행*은 되지만 *읽기*는 안 되는 권한입니다. 코드를 읽어서 분석하는 것을 막을 수 있습니다.
- 가드 페이지: 일부러 접근 불가로 둔 메모리 페이지입니다. 누가 건드리면 바로 예외가 나서 "누군가 여기를 뒤지고 있다"는 사실이 드러납니다.

## 3. 문제: 커널을 뺏기는 순간, 직전 기록이 사라진다

### 공격 시나리오: 경쟁 조건 공격(race condition attack)

Sysdig, eAudit 같은 기존 감사 도구는 로그 수집 모듈이 **게스트 커널 안**에 있습니다. 공격 흐름을 시간 순서로 그려 보면 이렇습니다.

```
t0  공격자가 취약점 공격 시작 ──▶ 이 행위가 로그로 기록되어 버퍼에 쌓임
t_c 커널 권한 획득 (침해 시점)
t1  공격자가 커널 버퍼를 뒤져 t0~t_c 사이 로그를 삭제
t2  (뒤늦게) 버퍼가 디스크로 저장됨 ──▶ 정작 침입 흔적은 이미 없음
```

논문에 따르면 기존 시스템에서 로그가 버퍼에 머무는 시간은 보통 **10~250ms** 이고, 공격자가 지우기에 충분한 시간이라고 합니다 [원문 p.594].

### 기존 해결책: "더 자주 옮기자" → 느려짐

그래서 기존 연구들은 로그가 버퍼에 오래 머물지 않게 만드는 쪽으로 갔습니다.

| 시스템 | 방식 | 대가 |
|---|---|---|
| OmniLog | 시스템 콜마다 하이퍼바이저로 진입해 로그 보호 | 매번 권한 전환(VM exit) → 매우 느림 |
| HitchHiker | 일정 주기로 신뢰 영역에 로그 제출 | 주기가 짧을수록 느리고, 길면 로그 손실 |
| eAudit | 시스템 콜 가중치 합이 임계값을 넘거나 16ms가 지나면 강제 제출 | 시스템 콜 경로에 검사·동기화 비용 추가 |

참고로 논문이 인용한 산업 조사에 따르면 기업은 감사 도구 오버헤드를 **최대 3%** 정도까지만 받아들인다고 합니다 [원문 p.593]. 기존 방식은 이 기준과 거리가 있었습니다.

### 논문이 짚은 근본 원인

저자들의 진단은 한 문장으로 요약됩니다.

> **수집 모듈이 커널과 붙어 있어서 공격자에게 보이기 때문에, 비싼 보호 장치를 덧댈 수밖에 없었다.** [원문 p.595~596]

즉 "로그를 빨리 옮기는 것"은 증상 치료였고, 진짜 문제는 "수집기가 공격자 눈에 보인다"는 것이었습니다.

### 이 논문이 지키겠다고 약속하는 범위 (중요)

- 지키는 것: 침해 시점 `t_c` **이전**에 생긴 로그의 무결성
- 지키지 않는 것: `t_c` **이후** 로그 (공격자가 커널을 쥔 뒤에는 무엇이든 조작할 수 있으므로)
- 믿는 것(TCB): 하이퍼바이저, Secure VM
- 범위 밖: 물리 공격, 사이드 채널 공격

"커널을 뺏겨도 모든 로그가 안전하다"는 뜻이 아니라는 점을 꼭 구분해야 합니다.

## 4. 핵심 아이디어: 수집기를 커널이 모르는 곳에 숨긴다

### 한 줄 요약

> 하이퍼바이저가 **게스트 커널이 모르는 메모리**에 수집기를 넣고, stage-2 권한으로 그 수집기를 지킨다. 수집기가 안 보이니 로그를 서둘러 옮길 필요가 없고, 그래서 **비동기**로 천천히 가져가도 된다.

### 구성 요소 3개

```
┌──────────── 감사 대상 VM ────────────┐       ┌──── Secure VM ────┐
│  앱 ─syscall─▶ [숨은 수집기] ─▶ 원래 커널 │       │ 로그 수신          │
│                    │                 │       │  → 압축           │
│                    ▼                 │ 공유  │  → 디스크 저장      │
│              [보호된 로그 버퍼] ─────────┼──────▶│  → 나중에 해석      │
└──────────────────────────────────────┘ 버퍼  └───────────────────┘
                 ▲ 주입·보호(stage-2)
          ┌──────┴──────┐
          │  하이퍼바이저  │
          └─────────────┘
```

1. **주입된 수집 모듈**: 시스템 콜을 가로채 인자와 반환값을 기록합니다.
2. **하이퍼바이저**: VM이 부팅될 때 수집기를 숨은 영역에 넣고 stage-2로 보호합니다.
3. **Secure VM**: 공유 버퍼에서 로그를 비동기로 끌어가 압축·저장합니다.

### 시스템 콜 하나가 처리되는 순서

1. 앱이 시스템 콜을 부릅니다.
2. 커널의 시스템 콜 진입 지점에 하이퍼바이저가 심어 둔 점프 명령 때문에 실행 흐름이 숨은 수집기로 넘어갑니다.
3. 수집기가 시스템 콜 번호, 인자, 프로세스 정보를 챙깁니다.
4. 수집기가 원래 커널의 시스템 콜 처리 함수를 **함수처럼 호출**합니다.
5. 처리가 끝나면 다시 수집기로 돌아와 반환값을 붙이고 버퍼에 씁니다.
6. Secure VM이 버퍼를 계속 읽어가 저장합니다.

### 이걸 구현하려면 풀어야 했던 문제 3개

저자들은 "커널에 의존하지 않는 수집기"를 만들려면 세 가지 어려움이 있다고 정리합니다 [원문 p.597]. 각각을 어떻게 풀었는지 제 말로 정리하면 이렇습니다.

**(C1) 커널 도움 없이 어떻게 메모리에 올리나?**
보통 커널 모듈이나 eBPF 프로그램은 커널이 메모리를 내주고 검증해 줍니다. HyperAudit은 하이퍼바이저가 VM을 만들 때 메모리 일부("Critical Space")를 따로 떼어 두고, **VM에게는 그 영역이 있다는 사실을 알려주지 않습니다.** 그러니 `lsmod` 같은 명령으로도, 게스트가 볼 수 있는 메모리를 훑어도 수집기가 보이지 않습니다. 신뢰는 "부트로더 → 하이퍼바이저 → Secure VM과 수집기 체크섬 확인" 순서로 이어집니다.

**(C2) 실행 중에 어떻게 지키나?**
stage-2 권한으로 막습니다.

| 영역 | stage-2 권한 | 공격자가 시도하면 |
|---|---|---|
| 수집기 코드, 점프를 심은 커널 코드 | 실행 전용(XO) | 코드를 읽어 버퍼 주소를 알아내려 하면 트랩 |
| 수집기 데이터, 수집기용 페이지 테이블 | 읽기 전용(RO) | 수정 시도 시 트랩 |
| 로그 버퍼 주변 | 가드 페이지(매핑 안 함) | 주변을 훑으면 트랩 |

버퍼 숨기기가 특히 재미있습니다. stage-1에서는 **1GB 크기 페이지 하나**로 가드 영역과 버퍼를 통째로 매핑해서, 겉으로 보기엔 1GB 전체가 쓸 수 있는 메모리처럼 보입니다. 하지만 stage-2에서는 진짜 버퍼 페이지만 연결하고 나머지는 비워 둡니다. 버퍼 위치는 적재할 때마다 무작위로 바뀝니다. 그래서

- 앞에서부터 차례로 훑으면 → 반드시 가드 페이지를 밟고 트랩
- 아무 데나 찍으면 → 맞힐 확률이 0.1% 미만 [원문 p.598]

이 됩니다. 비유하자면 "1GB짜리 지뢰밭 한가운데 아주 작은 금고를 묻어 두고, 금고 위치를 적은 쪽지는 읽을 수 없는 잉크로 써 둔" 구조입니다.

**(C3) 커널 도움 없이 어떻게 인자를 읽나?**
VMI(가상 머신 내부 관찰) 방식처럼 하드웨어 상태를 직접 읽습니다.
- 시스템 콜 번호와 인자: CPU 레지스터에서 읽습니다.
- 파일 경로 같은 포인터 인자: 시스템 콜이 **끝난 뒤에** 읽습니다. 그 사이 커널이 필요한 페이지를 메모리에 올려 두기 때문입니다.
- 프로세스·스레드 구분: x86은 `cr3`(페이지 테이블 주소)와 `%gs` 영역, Arm은 `TTBR0_EL1`과 `SP_EL0`를 씁니다.
- "fd 3번이 어떤 파일인가" 같은 의미: 기록 시점에는 숫자만 남기고, 나중에 Secure VM이 앞선 `openat`, `socket` 기록과 이어 붙여 복원합니다.

### 성능을 위한 작은 아이디어 2개

- **스택으로 짝 맞추기**: 시스템 콜의 시작(인자)과 끝(반환값)을 짝지을 때, 기존 eBPF 도구들은 스레드 ID를 키로 한 해시맵을 썼습니다. 스레드가 많아지면 충돌과 락 대기가 생깁니다. HyperAudit은 시스템 콜을 부른 **스레드 자신의 스택**에 인자를 잠깐 올려 두고, 처리가 끝난 뒤 같은 자리에서 꺼냅니다. 같은 스레드의 스택이니 락이 필요 없습니다.
- **로그 압축**: 꼭 필요한 필드만, 필요한 바이트 수만큼만 쓰고, 같은 스레드의 연속 로그는 PID를 생략합니다. 평균 로그 길이가 약 17바이트로, Sysdig(약 111~126바이트)보다 훨씬 짧습니다 [원문 p.599, p.603].

### 구현

- x86: KVM(Linux 6.17.1) + kvmtool 수정. `entry_SYSCALL_64` 안에서 `do_syscall_64`를 부르기 직전에 점프를 심습니다.
- Arm: Rust-Shyper 하이퍼바이저, RK3588 보드. `el0_sync`에서 핸들러로 가기 직전에 점프를 심습니다.
- 추가한 코드 양이 작습니다. x86 기준 수집기 329줄, 하이퍼바이저 486줄, Secure VM 1047줄입니다 [원문 p.600].

## 5. 결과, 그리고 걸리는 점

### 보안 평가: 진짜 못 지우나?

DirtyPipe(CVE-2022-0847)로 권한을 올린 뒤 버퍼를 찾아 침해 전 로그를 지우는 실험을 10번 반복했습니다 [원문 p.601].

| 대상 | 침해 전 로그 손실률 (최소/평균/최대) |
|---|---|
| HitchHiker, 1ms 주기 제출 | 0.2 / 1.1 / 2.5 % |
| HitchHiker, 15ms 주기 제출 | 0.5 / 43.9 / **100** % |
| **HyperAudit** | **0 / 0 / 0 %** |

HyperAudit은 "지우기" 단계까지 가지도 못했습니다. 버퍼를 찾으려고 페이지 테이블을 훑으면 가드 페이지에서, 코드를 읽으면 XO 위반으로 하이퍼바이저에 걸렸기 때문입니다.

홍수 공격(이벤트를 대량으로 만들어 버퍼를 넘치게 하는 공격)도 시험했습니다. `getpid`를 점점 더 빠르게(50 events/ms씩 증가) 부르게 했을 때 Sysdig는 350 events/ms부터 로그를 잃기 시작해 1200 events/ms에서 70%를 잃었고, HyperAudit은 50~1200 events/ms 구간에서 손실이 없었습니다 [원문 p.602].

### 성능 평가: 빨라졌나?

| 항목 | 결과 |
|---|---|
| 로그를 많이 만드는 앱 5종(PostMark, Nginx, Apache2, Memcached, Redis) 기하평균 오버헤드 | x86 **8.59%**, Arm **12.74%** |
| 같은 조건에서 비교 대상 대비 감소율 (x86) | Sysdig 대비 48.7%, eAudit 대비 49.3%, OmniLog 대비 88.9% 낮음 |
| 같은 조건에서 비교 대상 대비 감소율 (Arm) | Sysdig 대비 22.1%, HitchHiker 대비 66.8%, OmniLog 대비 74.3% 낮음 |
| 계산 위주 앱(7-zip, OpenSSL, Firefox) | 모든 도구가 2% 미만 |
| 스트레스 테스트 4종 기하평균 | x86 20.16%, Arm 19.43% (비교 대상 중 최저) |

가장 설득력 있었던 건 **제거 실험(ablation)** 입니다. 같은 4개 앱에서 [원문 p.604]

- 기본 HyperAudit: 2.07%
- 비동기 대신 **동기 제출**로 바꾸면: 70.07%
- 스택 대신 **해시맵**으로 짝 맞추면: 5.27%

즉 "숨겼기 때문에 비동기로 갈 수 있었다"는 주장이 숫자로 뒷받침됩니다. 오버헤드 대부분은 동기 제출에서 나왔습니다.

> 주의: 8.59%(앱 5종), 20.16%(스트레스 4종), 2.07%(제거 실험 앱 4종)는 서로 **다른 실험 집합**의 값입니다. 섞어서 비교하면 안 됩니다.

### 내 생각 — 걸리는 점 5가지

**① 하이퍼바이저를 믿는다는 전제가 크다.**
게스트 커널을 뺏긴 상황은 막아도, 하이퍼바이저나 Secure VM이 뚫리면 전부 무너집니다. 논문도 TCB로 명시했지만, 실제 클라우드에서 하이퍼바이저 취약점(VM escape)은 꾸준히 나옵니다. 마침 제 프로젝트가 바로 그 "하이퍼바이저 쪽이 뚫린 이후"를 보는 연구라서, 두 연구가 서로의 빈 곳을 덮는 관계라고 느꼈습니다.

**② 비교 대상 일부가 '진짜'가 아니다.**
OmniLog는 필요한 보드가 없어서 HyperAudit 위에서 "시스템 콜마다 하이퍼콜"로 흉내 냈고, Arm용 HitchHiker도 핵심 BPF만 가져와 다시 만든 버전입니다 [원문 p.602]. 공정성을 위해 경쟁 도구의 처리·저장 기능도 껐습니다. 이해는 되지만, "원래 도구 대비 몇 %"로 읽으면 과장이 됩니다.

**③ 숨기기는 '어렵게 만들기'이지 '불가능하게 만들기'는 아니다.**
무작위 접근 적중률 0.1% 미만은 한 번 시도 기준입니다. 공격자가 트랩이 나도 상관없다고 생각하고 여러 번 찍으면 어떻게 되는지, 그리고 트랩이 났을 때 하이퍼바이저가 VM을 멈추는지 기록만 하는지는 논문에서 명확히 다루지 않습니다. 또 사이드 채널(TLB, 캐시)로 버퍼 위치를 알아내는 공격은 범위 밖으로 두고 완화 아이디어만 논의했습니다 [원문 p.605].

**④ 커널 버전이 바뀌면 손이 간다.**
점프를 심는 위치가 커널 내부 함수(`entry_SYSCALL_64`, `do_syscall_64`) 기준이라, 커널 버전마다 주입 위치를 조정해야 합니다. 논문은 "간단하다"고 하지만 실제 클라우드처럼 게스트 커널이 수백 종이면 관리 부담이 될 수 있습니다.

**⑤ 운영자가 테넌트를 몰래 볼 수 있는 기술이기도 하다.**
게스트 안에서는 수집기가 안 보이니, 클라우드 운영자가 고객 VM의 시스템 콜을 고객 모르게 볼 수 있습니다. 저자들도 윤리 절에서 동의·최소 수집·암호화를 전제로 해야 한다고 밝혔습니다 [원문 p.606]. "사용자 투명(User Transparent)"이라는 제목의 장점이 그대로 위험이 되는 부분입니다.

## 6. 배운 점과 앞으로 할 것

### 배운 점

- **성능 문제의 원인이 보안 구조에 있을 수 있다.** 기존 연구들이 "어떻게 더 빨리 옮길까"를 고민할 때, 이 논문은 "왜 옮겨야 하지?"를 물었습니다. 수집기를 공격자 시야에서 빼자 보호 비용이 통째로 사라졌습니다. 제 도구를 설계할 때도 "이 비용은 어떤 위협 때문에 내는가"를 먼저 따져 봐야겠다고 느꼈습니다.
- **위협 모델은 '지키는 범위'를 좁게 말하는 것이 신뢰를 만든다.** "침해 전 로그만 지킨다"고 선을 그어서 오히려 주장이 단단해졌습니다.
- **eBPF 감시 도구도 같은 공격에 노출된다.** eBPF도 커널 안에서 돌기 때문에, 커널을 쥔 공격자에게는 보이고 끌 수 있습니다. 제 도구는 게스트가 아니라 **호스트**에서 QEMU 프로세스를 보기 때문에 게스트 커널 장악에는 영향을 받지 않지만, VM escape 뒤 호스트 권한까지 올라간 공격자 앞에서는 HyperAudit 이전 도구들과 같은 처지가 됩니다.

### 앞으로 할 것

**① 이어서 읽을 논문**
- Paccagnella et al., *Logging to the Danger Zone* (CCS 2020) — 경쟁 조건 공격을 처음 체계적으로 정리한 논문
- Zhang et al., *HitchHiker* (CCS 2024) — 이 논문의 주요 비교 대상, 주기 제출 방식의 원조
- Sekar et al., *eAudit* (IEEE S&P 2024) — 빠른 로그 수집과 압축 인코딩
- Jiang et al., *Auditing Frameworks Need Resource Isolation* (USENIX Security 2023) — 홍수(super producer) 공격
- Garfinkel & Rosenblum, *VMI 기반 침입 탐지* (NDSS 2003) — HyperAudit이 영감을 얻은 VMI의 출발점

**② 다른 분야에 적용할 가능성**
- **컨테이너·쿠버네티스**: 컨테이너는 호스트 커널을 공유하므로 이 구조를 그대로 쓸 수 없습니다. 대신 Kata Containers나 Firecracker처럼 **VM으로 감싼 컨테이너**에서는 같은 아이디어로 "노드 커널을 뺏겨도 남는 감사 로그"를 만들 수 있을지 궁금합니다.
- **클라우드 포렌식**: AWS에서 사고가 나면 대개 VM 안의 로그(CloudWatch Agent 등)를 봅니다. 이 로그도 공격자가 지울 수 있다는 점에서, "침해 전 로그를 VM 밖에 두는" 발상은 포렌식 증거 보존 관점에서도 의미가 있습니다.

**③ 직접 재현·비교해 보고 싶은 것**
- Zenodo에 공개된 x86 버전을 받아 KVM 환경에서 PostMark 오버헤드와 경쟁 조건 실험을 다시 돌려 보기
- 가드 페이지 트랩이 났을 때 실제로 하이퍼바이저가 무엇을 하는지 코드에서 확인하기
- 같은 워크로드에서 Falco(eBPF 드라이버)와 HyperAudit의 로그 손실 시작점을 비교하기

**④ 내 연구로 발전시킨다면**
제 프로젝트는 "VM escape 이후 호스트의 QEMU 프로세스가 평소와 다르게 행동하는 것"을 eBPF로 잡는 도구입니다. HyperAudit을 읽고 두 가지 방향을 정했습니다.

1. **위협 모델에 "감시 도구 자체에 대한 공격"을 명시하기.** 지금은 "감시기를 무력화하는 공격은 범위 밖"이라고만 적어 두었는데, HyperAudit처럼 "탐지 시점 이전 이벤트는 어디까지 보장하는가"를 구체적으로 적어야 합니다.
2. **이벤트 손실을 평가 지표에 넣기.** HyperAudit의 홍수 실험처럼, 초당 이벤트 수를 단계적으로 올리며 제 eBPF 감시기가 언제부터 이벤트를 놓치는지 측정하겠습니다. 탐지율이 높아도 이벤트를 놓치면 의미가 없기 때문입니다.
